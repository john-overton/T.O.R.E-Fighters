## What John did, 2026-10-05

John ran the operations guide's deployment steps and put a master on the
internet at `master.jroverton.com`:

- The program listens on UDP 26901 (the main port: listings, introductions,
  the relay, statistics) and UDP 26902 (the router test's second port).
- DNS has an **A record** for `master.jroverton.com`, and John then added an
  **AAAA record**, so the name resolves over IPv4 and IPv6.
- The game's default master is that name and port, `master.jroverton.com:26901`
  (commit 913e7cfd, "Make master.jroverton.com the game's default master"). A
  player who changes nothing talks to it from that build on. The relay is on,
  the master's default (John's decision, [decisions](../MULTIPLAYER.md#decisions)).

Not recorded here, because the lead was not told and the repository cannot see
it: the machine's plan and region, and the exact build installed. Fill both in
from the server (`tore-master --version` prints the version and commit; the
journal's first lines say the relay settings).

## The flood check, from outside

The lead ran [the flood tool](../MASTER-SERVER.md#the-flood-tool) against the
public master from a home connection:

```sh
tore-master flood master.jroverton.com:26901 10
```

| Measure | Result |
| --- | --- |
| Datagrams sent in 10 seconds | 19,998 |
| Datagrams answered | 296 |
| Ports that were answered with more bytes than they sent | none |
| Verdict the tool printed | limits held |

So the master answered about 1.5 percent of a 2,000 datagrams a second flood
and never sent a port more than it received, which is the point of its
per-source limits: it cannot be used to aim traffic at someone else (an
amplification attack) and it keeps serving others while one source floods.

The tool's other check, a browse from a second source address during the
flood, was skipped, as the operations guide says it will be from outside: every
port at home is one source to the master. That check ran on loopback in the
battery's net lane (`net-master-flood`).

## Still open: John's manual checks

These need real networks and a real router, which an agent on one machine
cannot give. None has been done. Each line says what to do and what a pass
looks like. Use the public master (no `--master` option needed).

1. **A listed game, seen from outside.** Host a game from one network (the
   Internet Lobby's New, or a dedicated server with `broadcast on`). From a
   different network, open the Internet Lobby (or run `tore-app --browse 5`).
   Pass: the game appears within one heartbeat (30 seconds). Then stop the
   host without a clean quit (close the laptop, pull the cable). Pass: the
   game is gone from the list within 90 seconds.
2. **A join through the introduction from another network.** From that other
   network, join the listed game. Pass: Messages show the host's addresses
   being tried and a punched path; the lobby marks the player's path as
   direct or punched. Do this for a home router on each side, and, if you can,
   once with double NAT.
3. **A relayed join.** From a phone hotspot (CGNAT), join a listed game. Pass:
   nothing answers directly within 3 seconds, the game asks for the relay,
   Messages say so, and the player joins in about 4 seconds, marked as
   relayed. On the server, the journal shows `relay opened` and later `relay
   closed`, and the status line's `relay-month=` grows.
4. **Directly over IPv6.** With a host and a player that both have IPv6, join
   and check that the path shown is direct (the AAAA record makes the master
   reachable over IPv6; whether the game's own sockets use it is part of what
   this check finds out).
5. **Port mapping on his router.** `tore-app --map-port 30`. This changes the
   router, which is why no test does it. Pass: it prints the mapping and the
   outside address, holds it 30 seconds, removes it and exits 0; the router's
   own page shows the forward while it is held and not after. A router
   that does not forward the port makes it exit with an error.
6. **Each month:** the plan's transfer in the Linode Cloud Manager and the
   master's `relay-month=` figure.

The design's acceptance for I and J asks for connections that succeed on a
home router, through double NAT, over a phone hotspot (CGNAT) through the
relay, and directly over IPv6: checks 2, 3 and 4 above. The [IJ7
row](../ARCHITECTURE.md#master-server-and-connectivity) records which are done
as John reports them.

## What the lead and agents covered before this
