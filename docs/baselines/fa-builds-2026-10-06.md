# Fighters Anthology 1.0 against 1.02F, everything the import keeps

> **T.O.R.E: Tasteful Opinionated Reverse Engineered.**
> The thing being reverse engineered is the *experience*, not the executable. We
> trace what a player does and what the game does back, down to the numbers they
> would notice. How the original code achieved it is history: useful evidence,
> never a blueprint. If a sentence below reads like an instruction to reproduce

Measured on 2026-10-06 on the development machine (Linux), at `multiplayer`
`ade1f174` (T.O.R.E 0.1.3), by a research agent for the multiplayer lead. John
asked what a lobby with one player on the Fighters Anthology 1.0 disc and one
on the 1.02F patch would really be like, since the game draws and plays the
player's own retail art, sounds and data. Earlier work had shown that every
file the simulation reads is the same
([slice D3a](../formats/esa-installer.md#the-import-pack-under-both-builds),
[content digests, L1](../ARCHITECTURE.md#compatibility), the `net-content-builds`
scenario, L3). Nobody had compared everything a player sees and hears. This does.

## The short answer

The two imports are the same game. Of the 4,157 entries each import keeps,
4,106 are byte for byte the same, 50 differ by a four byte link timestamp in the
file header and nothing else, and one is the entry that says which build the
import came from. Every model, texture, palette, sound effect, music score and
recording, font, radio phrase, mission, terrain, HUD layout, menu, dialog and
the quick chat text is the same to the byte after the timestamp. A 1.0 player
and a 1.02F player see and hear the same thing in the same lobby. The only
place the build shows is a label and a one line note in the lobby.

The difference that does exist is in the retail files the import never reads
(the original executable, one retail menu and five pictures and fonts), and
none of it reaches T.O.R.E.

## Method

1. A 1.02F import and a 1.0 import, each into its own data folder, by two
   different paths (both write the same packs):
   - `tore-server --import gameassets/fighters-anthology --data-dir <a>` and
     `tore-server --import gameassets/fighters-anthology/disc1 --data-dir <b>`.
   - The game's own import, `TORE_DATA_DIR=<c> tore-app --import <folder>
     --import-only --no-audio`, for the same two folders. The game also decodes
     and checks the menu art, buttons, fonts and debrief art, so this proves the
     game accepts both. Its packs are byte for byte the server's.
2. The two packs compared entry by entry, name and bytes, with a short Python
   reader (the pack format is in `tore-import/src/pack.rs`: the 12 byte
   signature, a count, then length-prefixed name and bytes). Every difference
   was then read with the game's own module reader (`tore_formats::module::code`,
   which every DLG, MNU, HUD and MC reader in the game goes through) to see
   whether the part the game reads differs.
3. The retail source compared, which the import only partly reads: every entry of
   `FA_1.LIB`, `FA_2.LIB`, `FA_4B.LIB` and `FA_4D.LIB` from the installed 1.02F
   folder against the same archives inside the disc's `SETUP.ESA` (the
   installer container, `tore_formats::esa`), decoded and compared (all
   7,505 entries), and every file of the container against the installed folder
   by SHA-256.
4. The game's content digests for both imports with `tore-bot --content-report`
   (what the lobby compares): 14 aircraft, 16 theaters, 131 weapons and the
   shared data, 162 lines.

The comparison programs were throwaway examples and a script and are not part
of the repository. To repeat it: import both builds as above and compare the two
`menu-*.pack` files entry by entry; the report that `tore-bot --content-report`
prints must differ in its first line only.

## Every difference

### In the pack: 51 entries

All 50 module entries differ in the four bytes at file offset 136, the
`TimeDateStamp` of the module's header, and in no other byte. The 1.0 modules
were linked on 1997-08-12 and the 1.02F ones on 1998-03-13 (the stamps within
one build span about two minutes). The game never reads the header: every reader
takes the `CODE` section through `module::code`, which starts at file offset
512, and the 50 entries' code sections and base addresses are equal in both
packs (checked, 50 of 50). The entries differ in compressed size by one or two
bytes in the import report, which is the same change compressed.

The retail patch notes list what 1.02F fixed in the retail program: the
Pro Mission Creator's 3D rotation, a Windows 95 OSR2 join problem, a 52 frames
a second limit that stops fast computers from stretching the flight model (and
so giving a multiplayer player a better turn and roll rate), a frame rate
display in Jane's Online Gaming Center games, better Gaming Center mission
endings, and two rules about what is sent to its killboard. All are changes to
the retail program, none is data. T.O.R.E runs its own simulation at a fixed
120 Hz for every player ([ARCHITECTURE](../ARCHITECTURE.md)),
so the 1.0 machine-speed quirk does not exist in a T.O.R.E lobby and no
retail Gaming Center feature is part of it. The import hides none of these
differences; they are in `FA.EXE`, which T.O.R.E never runs.

### The loose files an import writes

A data folder holds the pack, `import-report.txt`, `media-source.txt` and the
logs. The report differs in its source and build lines, the `FA_1.LIB` entry
count (2,001 against 1,996), the offset of every entry inside the retail
archive (the 1.0 archives sit inside the container) and, for the 50 module
entries, the compressed size. `media-source.txt` records the folder the import
came from and is local to each machine. None is sent to another player.

## What a player would notice

1. **The build label.** The lobby's selected-player line reads, for example,
   "Goose: Fighters Anthology 1.0, on Linux", and Messages says once "Goose
   imported Fighters Anthology 1.0; the host, 1.02F. Every aircraft, weapon and
   theater is the same." (the joiner's own screen says "You imported ...").
   Nothing else on screen names the build.
2. **Nothing in the cockpit, the world or the sound.** Every aircraft shape,
   cockpit picture, HUD font, skin, theater, sky, explosion sheet, engine and
   weapon sound, radio phrase, music track and the quick chat messages are the
   same bytes in both imports.
3. **Nothing in the menus T.O.R.E draws.** The menu, dialog and HUD files differ
   only in a header field the game does not read, and the pictures and fonts
   they draw with are identical.
4. **What a player could notice is not about the build.** An import without
   `FA_4B.LIB` and `FA_4D.LIB` (a 1.02F install that did not copy the digital
   music) plays without recorded music, and one without `CHAT.TXT` has no quick
   chat messages. The importer says so in its summary and report. Neither is
   compared by the lobby (music and chat text are presentation), and neither
   depends on the build: the installed folder and the disc used here both carry
   both.

## Verdict for a mixed 1.0 and 1.02F lobby

A 1.0 player and a 1.02F player can share one lobby, one mission and one
flight, and neither can tell from the game that the other is on another build,
except for the label. The simulation is the same because every file it reads is
the same (all 162 content items match, and the join check of stage D compares
the files themselves). The presentation is the same because every file the
screens draw and the speakers play is the same bytes. Presentation was never
required to match between machines; here it does anyway. No difference in the
retail program (the frame rate limit, the Gaming Center changes, the H3D
eyewear) reaches a T.O.R.E game.

The lobby does not need to treat a 1.0 import as lesser, warn about it or
refuse it, and the build label and the "every aircraft, weapon and theater is
the same" line are accurate for every pair of unmodified imports. What would
break the claim is a different T.O.R.E import revision that keeps different
resources (the lobby already names an import made by an earlier T.O.R.E), a
modified archive (the content digests catch what the simulation reads), or a
third retail build (the importer refuses an executable it has not reviewed).

## What this did not check

- No game window was opened and nothing was listened to; "the same" is the
  same bytes through the same decoders, and the game's import path (with its
  art checks) accepts both.
- One installed 1.02F folder and one 1.0 disc were compared. Another copy of
  either could differ if it is damaged or modified; the importer's checks and
  the content digests are what catch that.
- The retail executable's behavior was compared by what T.O.R.E derives from
  it (four inert tables), the patch notes and the retail archives, not by
  running it.
